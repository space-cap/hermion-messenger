# PRD: 실데이터 기반 주식 모닝브리핑 구독 서비스

**버전**: v1.0
**작성일**: 2026.07.01
**작성자**: 이영현
**개발 환경**: Google Antigravity IDE

---

## 1. 배경 및 목적

기존 프롬프트 전용(LLM 브라우징 기반) 모닝브리핑은 거래대금·수급·종목 데이터에서 `(추정)` 태그가 발생하는 등 환각(hallucination) 문제가 있음. 본 서비스는 **DART/키움 공식 API 실데이터**를 기반으로 LLM은 "해설·요약"만 담당하도록 구조를 재설계하여, 신뢰 가능한 유료 구독 상품으로 전환하는 것을 목표로 함.

**핵심 원칙**: 숫자는 API가 만들고, LLM은 숫자를 창작하지 않는다.

---

## 2. 용어 정의

| 용어 | 정의 |
|---|---|
| 무료 티어 | 기본 지수/해외지수 요약만 제공되는 무료 구독 등급 |
| 유료 티어 | 수급 상세, 개인화 종목, 공시 요약이 포함된 유료 구독 등급 |
| 검증 레이어 | LLM 생성 텍스트의 숫자가 원본 API 데이터와 일치하는지 확인하는 자동화 로직 |
| 개인화 브리핑 | 구독자가 등록한 관심/보유 종목 기준으로 생성되는 브리핑 섹션 |

## 3. 전체 시스템 아키텍처

```
[스케줄러: 매일 07:00 KST 트리거]
        ↓
[1] 데이터 수집 레이어
    - 키움 REST API (국내 지수, 투자자별 매매동향, 실시간 시세, 개인화 종목 조회)
    - DART Open API (공시)
    - Yahoo Finance API (해외지수)
        ↓
[2] 데이터 정제·정규화 레이어
    - JSON 스키마로 통합
    - 결측치/이상치 검사, 실패 시 재시도(최대 3회) 후 알림
        ↓
[3] LLM 생성 레이어 (Claude API)
    - 시스템 프롬프트: "제공된 데이터 외 숫자 생성 금지"
    - 공통 브리핑 생성 (무료 티어 포함 공통 섹션)
    - 구독자별 개인화 섹션 생성 (유료 티어, 배치 처리)
        ↓
[4] 검증 레이어
    - 생성 텍스트 내 모든 숫자를 정규식/파싱으로 추출
    - 원본 API 데이터셋과 대조
    - 불일치 발견 시: 해당 브리핑 발송 보류 + 운영자 알림 + 재생성 1회 시도
        ↓
[5] 발송 레이어
    - 무료 티어: 카카오톡 오픈채팅 / 네이버블로그 게시 (08:30)
    - 유료 티어: 카카오 알림톡(개인) / 이메일 (07:30)
        ↓
[6] 구독/결제 관리 시스템
    - 구독자 DB (티어, 관심종목, 결제상태, 채널 선호)
    - 결제 연동 (토스페이먼츠/아임포트)
```

## 4. 기능 요구사항 (Functional Requirements)

### FR-1. 데이터 수집

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1.1 | 키움 API로 KOSPI/KOSDAQ 지수, 등락률, 거래대금을 매일 07:00 이전 조회한다 | High |
| FR-1.2 | 키움 API로 투자자별(외국인/기관/개인) 순매수 데이터를 조회한다 | High |
| FR-1.3 | DART API로 전일 18:00 ~ 당일 07:00 사이 공시를 조회하고, 구독자 관심종목과 매칭한다 | Medium |
| FR-1.4 | Yahoo Finance API로 전일 미국 3대 지수 및 필라델피아 반도체지수를 조회한다 | High |
| FR-1.5 | API 호출 실패 시 최대 3회 재시도하며, 최종 실패 시 발송을 보류하고 운영자에게 알림한다 | High |

### FR-2. 데이터 정제 및 정규화

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-2.1 | 각 API 응답을 공통 JSON 스키마로 변환한다 (예: `{index, value, change_pct, volume, ...}`) | High |
| FR-2.2 | 결측치나 값이 0/null인 항목은 별도 플래그 처리하여 LLM 프롬프트에서 "데이터 없음"으로 명시되게 한다 (임의 추정 금지) | High |

### FR-3. LLM 브리핑 생성

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-3.1 | 시스템 프롬프트에 "입력된 JSON 데이터에 없는 숫자는 절대 생성하지 않는다"는 제약을 명시한다 | High |
| FR-3.2 | 공통 브리핑(해외시장/국내시장/테마/뉴스/투자포인트)을 생성한다 | High |
| FR-3.3 | 테마·종목 언급 시, LLM 추론이 아닌 실제 등락률/거래량 상위 스크리닝 결과에서만 종목을 선택하게 한다 | High |
| FR-3.4 | 유료 구독자 개인화 섹션: 구독자가 등록한 종목 리스트를 입력받아 해당 종목의 API 데이터(전일 등락률, 관련 공시)만 반영한 섹션을 생성한다 | Medium |
| FR-3.5 | 브리핑 문구에 투자 권유·추천으로 해석될 수 있는 표현(예: "매수하세요", "지금이 기회")을 금지하는 프롬프트 가드레일을 포함한다 | High |

### FR-4. 검증 로직

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-4.1 | 생성된 브리핑 텍스트에서 숫자(지수, 등락률, 거래대금 등)를 추출한다 | High |
| FR-4.2 | 추출된 숫자를 원본 API 데이터와 비교하여 일치 여부를 판정한다 | High |
| FR-4.3 | 불일치 발견 시 해당 브리핑 발송을 자동 중단하고, 재생성을 1회 시도한다. 재생성 후에도 실패 시 운영자에게 즉시 알림한다 | High |
| FR-4.4 | `(추정)` 등 불확실성을 나타내는 표현이 텍스트에 포함되면 발송을 차단한다 | High |

### FR-5. 발송

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-5.1 | 무료 티어는 카카오톡 오픈채팅 및/또는 네이버블로그에 08:30 게시한다 | High |
| FR-5.2 | 유료 티어는 카카오 알림톡(개인 발송) 및 이메일로 07:30 발송한다 | High |
| FR-5.3 | 발송 실패(수신자 차단, API 오류 등) 시 재시도 로직 및 실패 로그를 기록한다 | Medium |

### FR-6. 구독/결제 관리

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-6.1 | 신규 가입 시 무료/유료 티어 선택, 관심종목 등록 폼을 제공한다 | High |
| FR-6.2 | 유료 결제는 정기결제(월 자동갱신) 방식으로 처리한다 | High |
| FR-6.3 | 구독 해지 시 다음 결제 주기부터 무료 티어로 자동 전환하거나 발송을 중단한다 | High |
| FR-6.4 | 환불 정책에 따른 청약철회(7일 이내) 요청 시 관리자가 수동 처리 가능한 관리 화면 또는 프로세스를 제공한다 | Medium |

## 5. 비기능 요구사항 (Non-Functional Requirements)

| ID | 요구사항 |
|---|---|
| NFR-1 | 전체 파이프라인(데이터 수집~발송)은 매일 07:30까지 완료되어야 함 (유료 티어 발송 마감 기준) |
| NFR-2 | API 키, 결제 정보 등 민감 정보는 환경변수/시크릿 매니저로 관리하며 코드에 하드코딩하지 않음 |
| NFR-3 | 구독자 개인정보(연락처, 관심종목)는 암호화하여 저장 |
| NFR-4 | 검증 레이어에서 발송 차단 발생 시 운영자에게 5분 이내 알림 도달 |
| NFR-5 | 시스템은 향후 구독자 수 1,000명 이상으로 확장 가능한 구조로 설계 (배치 처리 고려) |

## 6. 데이터 스키마 (초안)

### 구독자 (Subscriber)
```json
{
  "subscriber_id": "string",
  "name": "string",
  "phone": "string",
  "email": "string",
  "tier": "free | paid | vip",
  "watchlist": ["종목코드1", "종목코드2"],
  "channel_preference": "kakao | email | blog",
  "subscription_status": "active | cancelled | payment_failed",
  "created_at": "datetime"
}
```

### 일일 시장 데이터 (MarketDataSnapshot)
```json
{
  "date": "YYYY-MM-DD",
  "domestic_index": {
    "kospi": {"value": 0, "change_pct": 0, "volume_krw": 0},
    "kosdaq": {"value": 0, "change_pct": 0, "volume_krw": 0}
  },
  "investor_flow": {
    "kospi": {"foreign": 0, "institution": 0, "individual": 0},
    "kosdaq": {"foreign": 0, "institution": 0, "individual": 0}
  },
  "overseas_index": {
    "dow": {"value": 0, "change_pct": 0},
    "sp500": {"value": 0, "change_pct": 0},
    "nasdaq": {"value": 0, "change_pct": 0},
    "philadelphia_semi": {"value": 0, "change_pct": 0}
  },
  "disclosures": [
    {"company": "string", "title": "string", "url": "string"}
  ],
  "top_movers": [
    {"ticker": "string", "name": "string", "change_pct": 0, "volume": 0}
  ]
}
```

## 7. 개발 우선순위 (Milestone)

| 단계 | 내용 | 비고 |
|---|---|---|
| M1 | KRX/DART API 승인 완료 → 데이터 수집 스크립트 개발 | 승인 대기 중 |
| M2 | Claude API 프롬프트 설계 + 검증 로직(FR-4) 구현 | M1 완료 후 |
| M3 | 무료 티어 MVP: 카카오톡 오픈채팅 발송 테스트 | M2 완료 후 |
| M4 | 결제 시스템 연동 + 개인화 섹션(FR-3.4) 구현 | M3 검증 후 |
| M5 | 구독자 관리 화면, 환불 프로세스 구축 | M4와 병행 가능 |

## 8. 리스크 및 오픈 이슈

| 이슈 | 설명 | 담당/해결 방향 |
|---|---|---|
| KRX/DART API 응답 지연 시 07:30 발송 마감 못 지킬 가능성 | 재시도 로직 + 타임아웃 설정 필요 | M1 설계 시 반영 |
| 카카오 알림톡 발신 비용/승인 절차 | 알림톡 템플릿 사전 심사 필요 | M4 이전 카카오비즈니스 신청 |
| 검증 레이어 오탐(정상인데 불일치로 판정) | 숫자 포맷(콤마, 단위) 파싱 로직 정교화 필요 | M2 구현 시 테스트 케이스 확보 |
| 개인화 종목 수 증가 시 LLM 호출 비용 증가 | 배치 처리 또는 캐싱 전략 필요 | M4 확장 시 검토 |
